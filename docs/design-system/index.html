Overview

The design system behind EngenXT, a fleet-fuelling app used by drivers standing at a pump. This page is generated from the same CSS the product loads. Nothing on it is a copy.

Reading the stylesheet…

What it is for

Drivers use this app one-handed, outdoors, in daylight, with someone waiting behind them. That decides most of the system: high contrast, large targets, plain words, motion only where it costs nobody time.

Scope

Two pages share this system. index.html is sign-up plus the home screen. engenxt-onboarding.html is where a driver lands afterwards. Only index.html has moved to linked CSS so far, so the components documented here are the ones that page renders.

No build step, a requirement rather than a shortcut

No package manager, no bundler, no build step. Both pages open by double-clicking them. The deployed site is those same files served statically. A reviewer with no toolchain, on a plane, can open the product. That property is load-bearing, so the system lives in plain <link> tags, CSS custom properties and cascade layers. Never in a compiler.

Why layers rather than specificity

The order is declared once, at the top of tokens.css. A later layer beats an earlier one whatever the specificity. A screen's override no longer has to out-specify an atom. It lives further down the list instead. That keeps selectors flat and removes the reason people reach for !important.

There is one consequence. Two rules of equal specificity that relied on which was typed first will flip when they land in different layers. Splitting the stylesheet did that. The flips were caught by comparing every computed property on every element before and after. The rules involved were pinned into their original file, so today's rendering is preserved.

Pinning had a cost. Three .o-signup-sheet__resend rules stayed in atoms.css, against the filing law, because moving them might have moved pixels. That has since been tested rather than assumed. They are in organisms.css now. The fingerprint of all 104 states is unchanged. The conflict was real but it was not, in the end, a trade.

UI principles

Twelve rules the system already follows. Each one is stated so it can be checked, says where it is enforced and carries the exception the code actually takes. A principle with no stated exception is a principle somebody is quietly breaking.

Proximity and grouping

Every rendered gap inside a stage is 8, 16 or 24, with 32 only to close a centred group. Each number means exactly one thing. Looser steps are the base gap plus a margin on the element that starts them, never a base plus a nudge.

Enforced at: src/css/organisms.css:243-255: "The organism owns the vertical rhythm. Nothing in the markup sets spacing." Under ONE SCALE, THREE MEANINGS, "every rendered gap is 8, 16 or 24 and each number means one thing". 8 is parts of one thing (label to its field, field to its helper, the cells to the line that reports on them), 16 is one group to the next (the control block to the card about it), 24 is a decision or a different route. The reason follows: "Gaps used to be composed as 16 plus a 4px nudge, which rendered 18 and 20: values close enough to the group step to read as noise rather than meaning." The arithmetic is written on each rule: organisms.css:263 "8 + 8 = 16", :267 "8 + 16 = 24", :330 "8 + 24 = 32". Machine-checked at index.html:3854, ['Spacing', 'every rendered gap is on the scale', ... var ok = [4, 8, 16, 24, 32]].

The exception: Admitted and left unfixed at src/css/organisms.css:273-281. Gaps are authored between boxes: "a 48px target holds about 18px of line, so it carries ~15px of nothing above and below it. The eye is therefore shown roughly 23, 39 and 31 where the scale says 8, 24 and 16." The negative-margin correction was tried and "overshot: it tightened the button gap to 17 and closed the row to 1", so it "wants a designer looking at it rather than a blind correction". The measured gate passes. The eye does not.

Alignment

Alignment is decided by whether the thing has a neighbour to line up with, not by house style. A key-over-value stack is left-aligned only when it sits in a column that shares one reading edge. Standing alone on a centred panel, it centres. Any such override is scoped to the context, never written onto the atom.

Enforced at: src/css/organisms.css:128-140, .o-status-page__meta .m-figure { align-items: center; text-align: center; }. Consistency

A component reads tokens and never raw values. If a value has no token, the token is added first. Two gates hold it. Nothing painted may resolve to a value with no token. No token may be declared and never used. The only permitted unused tokens are on a named list saying which sibling flow spends each one.

How many tiers there are

A mature scale usually has two or three: a palette of raw values (--blue-60), a semantic layer that gives each one a job (--color-text-primary: var(--blue-60)) and sometimes a third per component. This one has a single tier named as though it had two.

Understand that before you change anything. The names already say what a value is for rather than what it is. That is the hard half of the work and it's done. What's missing is the indirection underneath. --color-text-primary holds #0d1e2a directly, so two roles that share a colour today have no way of saying they are the same colour. The counts below are measured from the live stylesheet, not asserted.

Do not "fix" this by adding a palette tier on a quiet afternoon. It is safe only if every value is preserved exactly. Prove that with the fingerprint instrument described under Traceability, not by eye. A half-done palette, where some roles point at it and some still hold literals, is worse than the single tier you started with.

The scale has a second setting

Fifteen tokens are declared twice. The second set lives under [data-text="large"] and takes over when the driver turns large text on. One attribute on the root resizes the whole flow, because no component holds a font size of its own.

This is the payoff for having a type scale at all. It's easy to break without noticing. A hard-coded font-size: 15px looks identical to var(--text-body) until somebody switches this on. Then it's the one line of text on the screen that didn't grow.

The steps are not uniform. That is deliberate. Body sizes gain 2px, the three display sizes gain 4px and the OTP cell gains 8px so the digits keep their room. In proportion the smallest text grows most: around a fifth at --text-nano against a sixteenth at --text-figure. That is the right way round, since the small text is what people turn this on for.

The one token the page writes

--keyboard-inset is declared at 0px and owned at runtime. When the keyboard opens, the page writes the real height onto the device frame. Three layers size themselves against it: the sheet's height and max-height, the frame's own height, the drawn keypad.

The declaration earns its place. Every one of its six consumers was written as var(--keyboard-inset, 0px), so the property resolved only because each of them carried its own fallback. That made those fallbacks load-bearing rather than defensive. Drop one and the sheet collapses silently, with nothing to fail. Declared, the fallbacks become belt and braces and the property has a stated default.

Zero is the whole of the default. No other keyboard height belongs in the stylesheet. The real number comes from the operating system at runtime, so a second value here would be a guess competing with a measurement. The unmigrated page carries the declaration for token parity and does not consume it.

How spacing is applied

  • Gap, not margin, between children of a flex or grid container.
  • Container padding for internal boundaries.
  • A component does not impose its own external margins; the parent layout owns the space between components.
  • Inner spacing is smaller than the spacing that groups things. Proximity is what says what belongs together.

Code primitives

The rules that apply to bare elements, before any class exists. A primitive has no name you can call. You get it by using the element. It's the one layer a developer inherits without knowing it is there, so read it before you write anything.

All of it lives in src/css/foundations.css, inside @layer foundations. That's second of eight, so any atom, molecule or screen with an opinion beats these rules whatever the specificity. A primitive sets the default. It never wins an argument.

The reset

Three declarations, applied to everything including generated boxes. Border-box makes a width the width you see, so a padded field still fits its column. Zeroing margin and padding means somebody asked for every gap on the page. No browser default is quietly contributing. 

*, *::before, *::after { box-sizing: border-box; margin: 0; padding: 0; }

The ground

body paints the page colour and sets the family and ink that everything else inherits. It's the only place in the system that names a font family. Every other rule inherits it or is a bug. 

body {
  min-height: 100vh;
  background: var(--color-surface-page);
  font-family: var(--font-sans);
  -webkit-font-smoothing: antialiased;
  color: var(--color-text-primary);
}

Form controls don't inherit type from their parent. Browsers hand them a system face instead, so the inheritance is repaired here by hand. button is stripped back to a plain box as well. Every button on the page then takes its appearance from a class rather than from the user agent. 

input, button, a { font-family: inherit; }
button { background: none; border: none; color: inherit; }

The focus ring

One ring for the entire system, two-tone on purpose. The dark core reads against the white sheet. The light halo around it reads against the near-black hero. A single-colour ring would disappear on one of the two. The sign-up flow uses both. 

:focus-visible {
  outline: 3px solid var(--color-focus);
  outline-offset: 2px;
  box-shadow: 0 0 0 6px var(--color-focus-halo);
}

:focus-visible rather than :focus, so the ring appears for a keyboard and not for a tap. Never remove it from a component. If it looks wrong on something you're building, that thing sits too tight against its neighbour. Give it room instead of taking the ring away.

Hiding

[hidden] is forced to display: none. It's the one !important in the foundations layer and it earns the place. A hidden child of a flex row still takes its share of the gap if something else set it to display: flex. That leaves a hole with no visible cause. 

[hidden] { display: none !important; }

Use the attribute, not a class. Hiding is state. Here, state is never a class.

The nudge

A wrong entry shakes the control the driver can actually correct: the field, not the screen. Moving the whole column moves the parts that are fine too. That reads as "everything is wrong" when one thing is. 

[data-shake="true"] { animation: shakeX var(--dur-slow) ease; }
Why it is on the field and not the card. Two animations on one element share one animation shorthand. When the shake finished, the shorthand fell back to the card's stageIn and replayed the entrance. Field, helper, card and button faded out then floated back up, half a second after the error appeared. Different elements, no shared property, no replay. Adding a second animation to an element that already has one is the trap.

@media (prefers-reduced-motion: reduce) { /* … */ }
[data-motion="reduced"] *, [data-motion="reduced"] *::before, … { /* … */ }

Both collapse animation and transition to 0.001ms rather than 0. Anything waiting on a transitionend or animationend event still receives it, so the flow doesn't stall. Both reset animation-delay and animation-iteration-count too. A staggered entrance won't leave the last element invisible for half a second. A loop won't run forever at a millisecond a turn.

They are !important and apply to every element, so a new component gets reduced-motion support for free. You write nothing. You do need the end state to be the readable one: if an element animates in from opacity: 0, it must not be left at zero when the animation is skipped.

Responsive behaviour

The product is a phone app. The design target is a phone, so there is no desktop layout to shrink from. What varies is the device width (390, 375, 360 and 320) and whether the keyboard is up.

The compression order

When the keyboard takes half the screen, space is given up in a stated order, starting with what the driver has already finished with: the tooling first, then the step counter, then instruction that has already been acted on, then the loose gaps. The base gap between related things goes last. It is what says which things belong together. That matters most when there is least room.

Content reflows by priority. Nothing is hidden merely to make it fit. No page scrolls sideways.

Accessibility

  • Keyboard. Every control is a real <button> or input. Disabled primary actions use aria-disabled, so they hold their place in the focus order and can still say why they are unavailable.
  • Visible focus. One ring for the whole product. It is two-tone, so it reads on the near-black hero and on the light sheet.
  • Labels. Persistent and visible. No placeholder-as-label anywhere.
  • Errors. Placed against the control they belong to. Colour never carries an error on its own: a field in error gains a glyph in its helper and shakes once.
  • Forced colours. @media (forced-colors: active) throws away every background and border colour. That is every cue the OTP group and the field have, so both re-express their state structurally: a solid outline for valid, a dashed one for error. The build gate fails any page missing that block, so nobody has to remember it.
  • Landmarks. Each screen is a <section> labelled by its own heading; the device chrome is aria-hidden.
  • Reduced motion. Honoured through the media query and through an explicit switch, so you can demo it without touching an OS setting.
  • Contrast. Sampled from rendered pixels on all 43 states, not reasoned about from tokens. Gradients and glass make the arithmetic unreliable.
  • Targets. A 48px floor, measured with pseudo-element extensions included. The drawn size and the pressable size are allowed to differ, so only the pressable one counts.

Known limitations

  • Screen-reader behaviour is reasoned about and coded for, but nothing has been run against a real screen reader.
  • The status-bar contrast check samples one point per state. It would miss a failure elsewhere in the bar.

The filing law

A rule is filed by the block that owns it (the leftmost in its selector), not by what it targets. .o-auth-hero__actions .a-btn is the hero's rule about a button it contains, so it belongs with the hero. Filing it under atoms would put a screen's override in front of the screen.

There is one live exception. It is not a good one: three .o-signup-sheet__resend rules sit in atoms.css, pinned there when the stylesheet was split so the rendering would not change. See Known limitations.

Adding a token

  1. It goes in the :root block of src/css/tokens.css.
  2. Its name must open with a sanctioned family. The gate keeps the list and fails the build for anything outside it: --color- --glass- --gradient- --kb- --font- --text- --weight- --leading- --tracking- --radius- --shadow- --sp- --size- --press- --z- --ease- --dur- --d-.
  3. Name it for what it is for, not for what it is.
  4. Add it to engenxt-onboarding.html as well. That page still carries an inline copy of the scale. The gate compares the two property by property, so a token in one file and not the other fails the build.
  5. If it is a type size, decide whether it also needs a value under [data-text="large"]. Fifteen tokens do.

Adding a component

  1. Pick the level from the table above; the prefix follows from it.
  2. Put it in that level's file, filed under its own leftmost block.
  3. Take --text-* for size rather than raw pixels, so it answers large text.
  4. Runtime state is a data-* attribute, never a class.
  5. If any state is signalled by colour alone, add a @media (forced-colors: active) branch restating it structurally. The gate requires that block to exist.
  6. Never remove the focus ring without drawing an equivalent on the component's own edge.
  7. Document it here. The gate fails if a block in src/css is never mentioned on this page.

How a token is named

A token opens with the family it belongs to: --color-, --text-, --sp-, --radius-, --dur- and the rest. The family is enforced. The gate keeps a list and a name outside it fails the build, so nobody can quietly start a --brand-blue-2 alongside the scale.

After the family, the name says what the value is for, not what it is. --color-text-secondary, not --color-grey-60. That is the rule that lets a value change without a rename. It is followed almost everywhere; see how many tiers there are for the count. --d- marks the developer panel, which never ships.

Token names are kebab-case, with one exception: --color-hover-onDark. That is not a slip. onDark is a single concept throughout this codebase (data-tone="onDark", .a-btn--outlineOnDark) and it is spelled the same way in all three places. The cost is that you cannot assume a token is kebab-case and autocomplete your way to it. It is the only one.

State is never a class

Runtime state rides a data-* attribute: data-state, data-tone, data-verdict. There is no is-open anywhere. The gate fails the build if one appears. A class says what a thing is; an attribute says what it is doing.

Known limitations and unresolved decisions

Approved and done

  • The resend button is organism-owned. It is now filed that way. Four rules style .o-signup-sheet__resend. Three of them sat in atoms.css, pinned there when the stylesheet was split. They now sit in organisms.css with the fourth. Visual correctness outranks a filing taxonomy, so the move was made and then measured. Every element on all 104 states is computed-identical before and after. The move stands. No cascade exception was needed. The countdown reads 500 while it waits and 600 once Resend is live. That is what the stylesheet says now, not what source order happened to produce.
  • Linked CSS, no build. Eight layer files loaded by plain <link>. Verified to render identically over file:// and http.
  • Cascade layers. Order declared once. Every rule is filed by its owning block, not its target, so a screen's override stays with the screen.
  • Gates keep their strictness. The three CLI gates learned to find linked CSS. Not one assertion was relaxed.

Implementation assumptions

  • A rule is filed by the leftmost block in its selector. .o-auth-hero__actions .a-btn is the hero's rule about a button it contains, so it lives with the hero.
  • An at-rule is filed by what it contains, so a media override lands beside the rules it overrides rather than in front of them.

Inconsistencies that need a design ruling

  • The semantic spacing layer. Approved and built. Seven aliases, each mapped one-to-one onto the reference step it already rendered, so no pixel moved. Adoption is the open part. Most --sp-* uses were left where they are, because picking which of two near-identical values is intended takes a design review. See Foundations.
  • Same-level nesting. Three components hold another of their own level: a-icon-btn holds a-badge, m-app-bar holds m-brand-lockup, m-alert holds m-privacy. Strictly, each pair is one level up. The build deliberately doesn't fail on these. A gate that fails on judgement calls teaches people to reach for the exception list.

  • Organisms are described here rather than rendered. They are full screens and need the device frame to make sense.
  • Only index.html is migrated. Until the app follows, its components stay documented in its own in-page spec panel.
