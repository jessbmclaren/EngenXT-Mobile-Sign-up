Overview

The design system behind EngenXT, a fleet-fuelling app used by drivers standing at a pump. This page is generated from the same CSS the product loads. Nothing on it is a copy.

Reading the stylesheet…

What it is for

Drivers use this app one-handed, outdoors, in daylight, with someone waiting behind them. That constraint decides most of the system: high contrast, large targets, plain words, and motion only where it costs nobody time.

Scope

Two pages share this system. index.html is sign-up and the home screen; engenxt-onboarding.html is what a driver arrives in afterwards. Only index.html has been migrated to linked CSS so far, so the components documented here are the ones that page renders.

Architecture

No build, and why that is a requirement rather than a shortcut

There is no package manager, no bundler and no build step. Both pages open by double-clicking them, and the deployed site is those same files served statically. A reviewer with no toolchain, on a plane, can open the product. That property is load-bearing, so the system is expressed in plain <link> tags, CSS custom properties and cascade layers — never in a compiler.

Dependency direction

Everything flows one way. A layer may use what is above it and must not reach down.

Two honest exceptions to the table above. The prototype does load developer.css — it is the eighth <link> in index.html — because the demo tooling has to work in the deployed prototype. It is last in the layer order, so it cannot affect how a product component renders; it is the one file to drop when the prototype becomes a product. And five tooling rules live in templates.css rather than in the developer layer, three of which read --d- tokens. The scale states that no product component may read a --d- token; these are tooling wearing a product file's name, and they should move.

Why layers rather than specificity

The order is declared once, at the top of tokens.css. A later layer beats an earlier one whatever the specificity — so a screen's override no longer has to out-specify an atom, it simply lives further down the list. That is what keeps selectors flat and removes the reason people reach for !important.

It has one consequence worth knowing. Two rules of equal specificity that relied on which was typed first will flip when they land in different layers. Splitting the stylesheet did exactly that, and the flips were caught by comparing every computed property on every element before and after. The rules involved were pinned into their original file so today's rendering is preserved.

The cost of pinning is that those rules are now filed against the naming law: three .o-signup-sheet__resend rules sit in atoms.css. Preserving the pixels and obeying the filing law are in genuine conflict there, and resolving it needs a design decision rather than a refactor — see Decisions.

How a token is named

A token opens with the family it belongs to — --color-, --text-, --sp-, --radius-, --dur- and the rest. The family is enforced: the gate keeps a list, and a name outside it fails the build, so nobody can quietly start a --brand-blue-2 alongside the scale.

After the family, the name says what the value is for, not what it is. --color-text-secondary, not --color-grey-60. This is the rule that lets a value change without a rename, and it is followed almost everywhere — see how many tiers there are for the count. --d- marks the developer panel, which never ships.

Token names are kebab-case, with one exception: --color-hover-onDark. That is not a slip. onDark is a single concept throughout this codebase — data-tone="onDark", .a-btn--outlineOnDark — and it is spelled the same way in all three places. The cost is that you cannot assume a token is kebab-case and autocomplete your way to it. It is the only one.

State is never a class

Runtime state rides a data-* attribute — data-state, data-tone, data-verdict. There is no is-open anywhere, and the gate fails the build if one appears. A class says what a thing is; an attribute says what it is doing.

Tokens

Read out of the live stylesheet when this page loads. Nothing below is typed by hand, so a token cannot be documented at a value it no longer has.

The scale is copied verbatim into both pages, and the build gate compares them property by property — a token that exists in one file and not the other fails the build. Names must belong to a sanctioned family; a stray --brand-blue-2 is refused.

How many tiers there are

A mature scale usually has two or three: a palette of raw values (--blue-60), a semantic layer that gives each one a job (--color-text-primary: var(--blue-60)), and sometimes a third per component. This one has a single tier, and it is named as though it had two.

That is worth understanding before you change anything. The names already say what a value is for rather than what it is — which is the hard half of the work, and it is done. What is missing is the indirection underneath: --color-text-primary holds #0d1e2a directly, so two roles that happen to share a colour today have no way of saying they are the same colour. The counts below are measured from the live stylesheet, not asserted.

Do not "fix" this by adding a palette tier on a quiet afternoon. It is a safe change only if every value is preserved exactly, and the way to prove that is the fingerprint instrument described under Traceability — not by eye. A half-done palette, where some roles point at it and some still hold literals, is worse than the single tier you started with.

The scale has a second setting

Fifteen tokens are declared twice. The second set lives under [data-text="large"] and takes over when the driver turns large text on — one attribute on the root, and the whole flow resizes, because no component holds a font size of its own.

This is the payoff for having a type scale at all, and it is easy to break without noticing: a hard-coded font-size: 15px looks identical to var(--text-body) until somebody switches this on, and then it is the one line of text on the screen that did not grow.

The steps are not uniform, and that is deliberate. Body sizes gain 2px, the three display sizes gain 4px, and the OTP cell gains 8px so the digits keep their room. In proportion that means the smallest text grows most — around a fifth at --text-nano against a sixteenth at --text-figure — which is the right way round, since the small text is what people turn this on for.

Primitives

The rules that apply to bare elements, before any class exists. A primitive has no name you can call — you get it by using the element. That makes this the one layer a developer inherits without knowing it is there, so it is the one most worth reading before you write anything.

All of it lives in src/css/foundations.css, inside @layer foundations — second of eight, so every one of these rules is beaten by any atom, molecule or screen that has an opinion, whatever the specificity. A primitive sets the default. It never wins an argument.

The reset

Three declarations, applied to everything including generated boxes. Border-box means a width is the width you see, so a padded field still fits its column. Zeroing margin and padding means every gap on the page was asked for by somebody — there is no browser default quietly contributing. 

*, *::before, *::after { box-sizing: border-box; margin: 0; padding: 0; }

The ground

body paints the page colour and sets the family and ink that everything else inherits. It is the only place in the system that names a font family; every other rule inherits it or is a bug. 

body {
  min-height: 100vh;
  background: var(--color-surface-page);
  font-family: var(--font-sans);
  -webkit-font-smoothing: antialiased;
  color: var(--color-text-primary);
}

Form controls do not inherit type from their parent — browsers give them a system face instead — so the inheritance is repaired explicitly, and button is stripped back to a plain box so that every button on the page gets its appearance from a class rather than from the user agent. 

input, button, a { font-family: inherit; }
button { background: none; border: none; color: inherit; }

The focus ring

One ring for the entire system, and it is two-tone on purpose. The dark core reads against the white sheet; the light halo around it reads against the near-black hero. A single-colour ring would disappear on one of the two, and the sign-up flow uses both. 

:focus-visible {
  outline: 3px solid var(--color-focus);
  outline-offset: 2px;
  box-shadow: 0 0 0 6px var(--color-focus-halo);
}

:focus-visible rather than :focus, so the ring appears for a keyboard and not for a tap. Never remove it from a component. If it looks wrong on something you are building, the something is too tight against its neighbour — give it room rather than taking the ring away.

Hiding

[hidden] is forced to display: none. This is the one !important in the foundations layer and it earns its place: a hidden child of a flex row still takes its share of the gap if something else set it to display: flex, which leaves a hole nobody can see the cause of. 

[hidden] { display: none !important; }

Use the attribute, not a class. Hiding is state, and state is never a class here.

The nudge

A wrong entry shakes the control the driver can actually correct — the field, not the screen. Moving the whole column moves the parts that are fine too, which reads as "everything is wrong" when one thing is. 

[data-shake="true"] { animation: shakeX var(--dur-slow) ease; }
Why it is on the field and not the card. Two animations on one element share one animation shorthand. When the shake finished, the shorthand fell back to the card's stageIn and replayed the entrance — field, helper, card and button faded out and floated back up half a second after the error appeared. Different elements, no shared property, no replay. If you ever add a second animation to an element that already has one, this is the trap.

Motion

Every keyframe in the system is declared here, so a component can reach for an existing movement instead of inventing a near-copy. Read out of the live stylesheet below, at a fixed demo duration — in the product each one plays at its own duration token.

Durations and easings are tokens, not numbers: --dur-fast through --dur-slow, and four easings. --ease-out is the default for anything arriving, --ease-emphasis for the sheet, --ease-spring only where an overshoot is wanted. Full values are in Tokens under Duration and Easing.

Reduced motion is honoured twice

Once for the operating system setting, and once for the demo toggle in the developer panel — because a stakeholder watching on a borrowed laptop cannot change the OS preference, and the flow still has to be reviewable with the movement off. 

@media (prefers-reduced-motion: reduce) { /* … */ }
[data-motion="reduced"] *, [data-motion="reduced"] *::before, … { /* … */ }

Both collapse animation and transition to 0.001ms rather than 0, so anything waiting on a transitionend or animationend event still receives it and the flow does not stall. Both reset animation-delay and animation-iteration-count too, so a staggered entrance does not leave the last element invisible for half a second and a loop does not run forever at a millisecond a turn.

Because they are !important and apply to every element, a new component gets reduced-motion support for free. You do not need to write anything. You do need to make sure the end state is the readable one: if an element animates in from opacity: 0, it must not be left at zero when the animation is skipped.

Spacing

A 4px base — --sp-1 through --sp-8, 4px to 32px — with two half-steps, --sp-1h (6px) and --sp-2h (10px), because both are structural here rather than exceptional. There is no 18: gaps that composed to 18 and 20 sat close enough to the group step to read as noise rather than meaning, and were removed. The tokens and their resolved values are in the Tokens table under Spacing.

Not yet done. A semantic spacing layer — space-control-inline, space-stack-related, space-section and the rest — has been specified but not built. Introducing it means re-pointing roughly 400 declarations and deciding, case by case, which of two near-identical values is the intended one. That is a design review, not a mechanical edit, and it changes pixels. It is listed under Decisions as awaiting approval.

How spacing is applied

  • Gap, not margin, between children of a flex or grid container.
  • Container padding for internal boundaries.
  • A component does not impose its own external margins; the parent layout owns the space between components.
  • Inner spacing is smaller than the spacing that groups things — proximity is what says what belongs together.

Atoms

Thirteen atom blocks exist in src/css/atoms.css; nine are rendered below. Twelve appear in the sign-up page's markup and the thirteenth, a-otp-cell, is created by script — it is shown here inside the m-otp-group specimen. Four have no specimen yet: a-spinner, a-scrim, a-notch and a-toast. Every specimen below is the real element with the real classes, drawn by the production CSS.

a-btn

.a-btnprimary · outline · disabled

Internal padding comes from --size-control as a minimum height, not from vertical padding, so a wrapped label cannot shrink the target. Press is --press-firm. Accessibility: disabled uses aria-disabled rather than the attribute, so the control keeps its place in the focus order and can still explain itself.

a-link

.a-linkdefault · quiet · flush

Minimum height is --size-target (48px) even where the text is small, because a link in this product is tapped with a thumb.

a-field and a-label

.a-fielddefault · error
Check the number and try again.

The field is a <label>, not a <span>. That is what makes the whole 56px box focus the input when a thumb lands anywhere on it. Geometry was tried first and was the wrong tool. In the sign-up flow the same element also carries m-phone-field — both classes on one element, because the field supplies the box and the molecule supplies the country prefix inside it.

The label is persistent, never a placeholder. The error message sits directly under the control it belongs to, and the field carries data-state="error".

What the error state actually changes: border colour and background, both colour. The non-colour cue is not the border width — the border is --size-border in every state. It is the glyph the helper gains beneath the field, and the shake on the control itself. Under @media (forced-colors: active), where every colour is discarded, the field restates itself structurally with outline: 2px dashed (atoms.css) — solid for valid, dashed for error. That branch is what keeps the state readable when colour is gone, and it is required by the build gate.

a-icon-wrap

.a-icon-wrapdefault · tones · bare

A fill, not an outline. The atom declares no color, deliberately: the glyph takes the ink of whatever row it is placed in, which is why a parent setting its colour is composition rather than an override.

.a-spinner · .a-handle · .a-progresssmall parts

Organisms

Four on this page: o-auth-hero, o-signup-sheet, o-status-page and o-outcome-panel. They are full screens rather than sections, which is discussed under Decisions.

They are not reproduced as specimens here. An organism in this product is a whole screen that positions itself absolutely inside the device frame and shows or hides on data-state — rendering one inside a documentation page would either require faking the frame or would cover the page. The honest way to see them is the real thing: open index.html and use the state rail, which lists all 43 states and deep-links to each.

Ownership. All four are product-specific. Nothing in the organism layer is shared between the two pages today — the shared core is tokens, foundations and the atom library.

Templates

t-device-frame

The phone. It owns the viewport the product is designed against — 390×844 by default, with 375, 360 and 320 available as a stress test — and it is the containing block every screen positions itself against.

It is also the one parent allowed to change what its children are, because it is the hardware: at the Android width the notch becomes a pill, and when the keyboard is up the sheet squares its corners and the hero's title steps down a size. A component cannot carry a modifier for that, because it is not the component's fact.

Honest limit. t-device-frame is content-agnostic, which is half of Frost's definition of a template, but it does not articulate a screen's content structure. The second page has a real t-screen template; this page does not yet need one, because it has a single sheet over a hero rather than twelve screens repeating a skeleton.

Accessibility

  • Keyboard. Every control is a real <button> or input. Disabled primary actions use aria-disabled so they keep their place in the focus order and can still explain why they are not available.
  • Visible focus. One ring for the whole product, two-tone so it reads on the near-black hero and the light sheet alike.
  • Labels. Persistent and visible. No placeholder-as-label anywhere.
  • Errors. Placed against the control they belong to, and never carried by colour alone — a field in error gains a glyph in its helper and shakes once.
  • Forced colours. @media (forced-colors: active) discards every background and border colour, which is every cue the OTP group and the field have. Both re-express their state structurally instead: a solid outline for valid, a dashed one for error. The build gate fails any page without that block, so this is enforced rather than remembered.
  • Landmarks. Each screen is a <section> labelled by its own heading; the device chrome is aria-hidden.
  • Reduced motion. Honoured through the media query and an explicit switch, so it can be demonstrated without changing an OS setting.
  • Contrast. Sampled from rendered pixels on all 43 states, not reasoned about from tokens — gradients and glass make the arithmetic unreliable.
  • Targets. A 48px floor, measured including pseudo-element extensions, because the drawn size and the pressable size are allowed to differ and only the pressable one counts.

Known limitations

  • Screen-reader testing has been reasoned about and coded for, but not performed with an actual screen reader.
  • The status-bar contrast check samples one point per state; it would miss a failure elsewhere in the bar.

Responsive behaviour

The product is a phone app, so the design target is a phone and there is no desktop layout to shrink from. What varies is the device width — 390, 375, 360 and 320 — and whether the keyboard is up.

The compression order

When the keyboard takes half the screen, space is given up in a stated order, from what the driver has already finished with: the tooling first, then the step counter, then instruction that has already been acted on, then the loose gaps. The base gap between related things is given up last, because it is what says which things belong together — and that matters most when there is least room.

Content reflows by priority. Nothing is hidden merely to make it fit, and no page scrolls sideways.

Decisions and open questions

Approved and done

  • Linked CSS, no build. Eight layer files loaded by plain <link>. Verified to render identically over file:// and http.
  • Cascade layers. Order declared once. Every rule is filed by its owning block, not its target, so a screen's override stays with the screen.
  • Gates keep their strictness. The three CLI gates learned to find linked CSS; not one assertion was relaxed.

Implementation assumptions

  • A rule is filed by the leftmost block in its selector. .o-auth-hero__actions .a-btn is the hero's rule about a button it contains, so it lives with the hero.
  • An at-rule is filed by what it contains, so a media override lands beside the rules it overrides rather than in front of them.

Inconsistencies that need a design ruling

  • The resend button is filed in the wrong place, and that is the real problem. Four rules style it. Three of them are in atoms.css even though their leftmost block is .o-signup-sheet__resend — an organism — which breaks the filing law stated above. Only one, align-self, is in organisms.css.

    The visible symptom: the countdown's weight is decided between .o-signup-sheet__resend:disabled (semibold) and .a-link:disabled (medium). Both are the same specificity and both are inside @layer atoms, so the layer order cannot separate them — source order alone decides, and medium wins. An earlier note here claimed layers would have flipped them and that they were pinned; that was wrong, and it was wrong because it assumed the rules were in the layers their names imply.

    Move the three rules to organisms.css and two things happen at once: the filing law holds again, and the layer order decides the weight instead of typing order — at which point "is 500 or 600 intended?" becomes a one-line answer rather than a standing question.
  • The semantic spacing layer. Specified, not built. It requires deciding, case by case, which of two near-identical values is intended, and it moves pixels.
  • Same-level nesting. Three components hold another of their own level — a-icon-btn holds a-badge, m-app-bar holds m-brand-lockup, m-alert holds m-privacy. Strictly each pair is one level up. The build deliberately does not fail on these, because a gate that fails on judgement calls teaches people to reach for the exception list.

Known limits of this page

  • Opened straight off disk, a browser will not let this page read the authored form of a token — only its resolved value. Serve the folder over http for the full table.
  • Organisms are described rather than rendered here; they are full screens and need the device frame to make sense.
  • Only index.html is migrated. The app's components are documented in its own in-page spec panel until it is.
